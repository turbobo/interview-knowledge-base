线程共享（VM 启动时创建）
非 JVM 规范区域
线程私有区域 随线程创建/销毁
程序计数器
Program Counter
不会 OOM
作用：字节码行号指示器，记录当前执行的指令地址
存放：字节码指令地址（native 方法时为 Undefined）
用途：线程切换后恢复执行位置、控制流（分支/循环/异常跳转）
唯一没有规定 OOM 的内存区域
Java 虚拟机栈
JVM Stack
会 OOM
作用：管理 Java 方法执行，每个方法创建一个栈帧
溢出：栈深度超限 → StackOverflowError
OOM：动态扩展时内存不足 → OutOfMemoryError
栈帧结构：
📦 局部变量表（基本类型 + 对象引用）
📊 操作数栈（计算中间结果）
🔗 动态链接（指向运行时常量池的方法引用）
↩️ 方法返回地址
本地方法栈
Native Method Stack
会 OOM
作用：为 Native 方法（C/C++ 实现）服务
HotSpot：与 Java 虚拟机栈合二为一
溢出：同虚拟机栈，可抛出 StackOverflowError
OOM：动态扩展时内存不足
线程共享区域 VM 启动时创建，所有线程共享
堆（Heap）
Garbage Collected Heap
会 OOM
作用：GC 主战场，存放几乎所有对象实例和数组
OOM：Java heap space 或 GC Overhead Limit Exceeded
堆内存分代结构：
← 新生代（Young Generation）→ ← 老年代（Old Generation）→
Eden 区（~80%）
S0
S1
Old Gen
新对象在此分配，Minor GC 频繁回收 长存活对象，Major/Full GC
比例：Eden : S0 : S1 = 8 : 1 : 1（默认）
晋升：对象年龄达到阈值（默认 15）或 Survivor 空间不足时晋升老年代
方法区（Method Area）
Method Area / Metaspace
会 OOM
作用：存储类元数据、方法字节码、常量池
OOM：java.lang.OutOfMemoryError: Metaspace
运行时常量池（Runtime Constant Pool）
编译期生成的字面量和符号引用。受方法区容量限制，可触发 OOM。
字符串常量池（String Pool）
JDK 1.7 起从永久代移至 Java 堆中，便于 GC 回收。通过 String.intern() 复用字符串。

方法区实现演进（JDK 版本变化）

JDK 1.7 及更早
实现为 永久代（PermGen），使用 JVM 管理的堆内存。
通过 -XX:MaxPermSize 设置上限（默认约 82MB）。
静态变量和字符串常量池也在此区域。
JDK 1.7（过渡）
字符串常量池和静态变量 移至 Java 堆。
永久代仍然存在，但内容减少。
JDK 1.8+
永久代被 元空间（Metaspace） 完全替代。
使用 本地内存（Native Memory），不再受 JVM 堆大小限制。
通过 -XX:MaxMetaspaceSize 设置上限（默认无上限）。
变更原因：永久代容量受限、GC 效率低、HotSpot 与 JRockit 合并（JRockit 无 PermGen）
非 JVM 规范区域 不属于运行时数据区，但常用
直接内存（Direct Memory）
Off-Heap Memory / Direct Buffer
会 OOM
来源：JDK 1.4 NIO 引入，通过 DirectByteBuffer 在堆外分配内存
作用：减少 I/O 场景下 JVM 堆与 Native 内存之间的数据拷贝，提升性能
限制：受物理内存和 -XX:MaxDirectMemorySize 参数限制
场景：NIO 文件读写、Netty、高性能缓存
注意：不受 GC 直接管理，通过 System.gc() 或 Cleaner 释放
